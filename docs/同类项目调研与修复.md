# 0.1.2：阅读顺序、排版与本地速度

调研日期：2026-10-02。先阅读同类项目的实际源码，再独立实现并验证适合 AM 的部分。调研不是对整个项目的质量排名，也不是“别人用了就必然更好”。没有复制或打包这些项目的源代码；KISS 的源码按其 GPL-3.0 许可提供，另外两个仓库未找到 LICENSE，均仅用于理解处理流程。

视口内保持文档阅读顺序、云端乱序结果按派发顺序提交，是针对用户要求在上述机制基础上作的 AM 适配；不声称这些仓库都提供完全相同的排序策略。

## 确认的问题

1. 0.1.1 按段落起点到视口顶部的绝对距离排序。长段落已读到中部时，起点可能在屏外；后方短段落反而更靠近视口顶部，容易先翻译。多批预派发又会保留滚动前的位置。
2. Sphinx 等网页的 HTML 源码经常为维护方便人工换行，浏览器正常排版会合并这些空白。旧序列化保留源码换行，译文又使用 `pre-wrap`，模型产生的换行和中文词间空格被放大显示。
3. 本地极速请求仍携带多段 JSON、重复上下文、长保护标记及相关术语描述，并等待整批输出。本轮通过缩短请求和及时提交当前一段减少首译等待，没有更换或下载用户模型。

## 具体行为

- 可见段落按 DOM 顺序优先；其次是下方邻近区域，再是上方。每次派发重新读取位置，不按字数优先。
- 本地极速每次处理一个段落；精准和云端保留用户批次设置。派发容量等于配置的并发数，本机默认 1。云端并发完成顺序不同也按阅读顺序显示。
- 已经发出的模型请求允许完成；滚动后的下一次派发使用新位置。不会因为连续滚动反复取消并重做正常推理。
- 只合并普通正文源码空白。真实 `<br>` 作为保护节点保留；明确使用 `pre-line/pre-wrap` 的段落保留换行；代码、公式内部空白完全保留。
- 中文正文的多余词间空格及中文标点旁空格清理可跨强调/链接边界，不删除英文单词间空格、单位或代码空格。
- 本地极速将长保护标记临时映射成短标记；响应恢复原标记并检查数量及格式嵌套。失败自动回到已有受校验的结构化路径。
- 本地极速术语分析延后到空闲时启动，新阅读任务可中断后台分析。精准仍保留更丰富的上下文和术语策略。
- 缓存使用实际参与该请求的上下文及相关译名；段落源文改变后，旧任务的响应不会覆盖新内容。

## 验证结果与边界

真实测试使用用户现有 `qwen3.8:27b-mlx`，学术＋极速、数学领域、上下文 8K、并发 1。在同一 Mathematics in Lean C02 §2.4 的 “It is an interesting fact that …” 长段落，按旧版→新版串行比较，均从空扩展缓存开始：

| 指标 | 0.1.1 | 本次修复 |
| --- | ---: | ---: |
| 浏览器显示目标段落译文 | 20.312 秒 | 7.100 秒 |
| 模型接口请求时间 | 19.466 秒 | 6.303 秒 |
| 实际输入 tokens | 1,847 | 381 |
| 实际输出 tokens（旧版包含同批其他段落） | 619 | 228 |
| 目标段落代码/公式表示、链接 | 13 个 code、1 个链接 | 13 个 code、1 个链接 |

该结果是**这一次目标长段落的首译延迟**，不是吞吐量提高三倍的证明，也不是所有页面或模型的速度保证。旧版→新版的顺序测试可能受模型温热和系统负载影响。未降低用户设置的上下文上限，未改 Ollama 配置或重启服务。翻译语义未经过数学专家全面审校。

浏览器验收还覆盖：跨屏长段优先、滚动后的新目标选择、待发任务数量限制、云端响应乱序、动态源文变化、词库局部重译、缓存、32 秒请求在关闭侧栏并终止服务后台后继续、真实代码/公式恢复，以及正文换行和代码空白的区别。
